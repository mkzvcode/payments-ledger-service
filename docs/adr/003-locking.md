# ADR 003: READ COMMITTED, порядок блокировок и version

Статус: принято.

Контекст: два списания могут прочитать один остаток. Только optimistic locking потребовал бы повторов всей команды при конкуренции. Встречные переводы создают риск deadlock.

Решение: явная транзакция READ COMMITTED. После резервирования ключа забираем все счета одним SELECT WHERE id = ANY(...) ORDER BY id FOR UPDATE. Все операции, включая deposit, следуют одному протоколу; строки transfer с FK создаются после захвата счетов. Планы балансов рассчитываются до первого UPDATE. Каждое обновление использует WHERE version = expected и version + 1. SQL-триггер требует увеличение версии ровно на единицу.

Последствия: сериализация команд на горячем счёте, ограниченная lock_timeout и statement_timeout. READ COMMITTED достаточно, потому что инварианты читаются под locks; он позволяет после ожидания увидеть commit конкурирующего владельца ключа. SERIALIZABLE добавил бы ненужные serialization failures. Другие writers обязаны соблюдать протокол; произвольный SQL, DDL и FK-locks других сервисов всё ещё могут создавать deadlock. Такие временные ошибки дают 503, клиент повторяет тот же ключ. Гарантия отсутствия deadlock относится к реализованным путям платежей и проверяется встречной нагрузкой.
