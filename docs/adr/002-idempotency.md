# ADR 002: идемпотентность в PostgreSQL

Статус: принято.

Контекст: клиент может не получить ответ после commit; параллельные повторы не должны создавать второй перевод. Один ключ с другим телом должен давать 422.

Решение: отдельная таблица idempotency_requests, key — PRIMARY KEY, hash SHA-256 от канонической последовательности kind/from/to/amount/currency. Резервирование через INSERT ON CONFLICT DO NOTHING в READ COMMITTED. Конкурентный insert ждёт commit; следующий statement видит результат. Перевод, журнал, балансы и сохранённый результат фиксируются в одной транзакции. Незавершённый резерв не может пройти commit благодаря constraint trigger.

Сохраняем успешное тело и доменные отказы, включая отказы без допустимой строки transfer. Новый requestId остаётся идентификатором текущего HTTP-запроса. Ошибки DTO и инфраструктуры не сохраняем. После rollback ключ можно повторить. Ключ глобален между deposit и transfer и хранится бессрочно. POST возвращает 201 и при повторе.

Последствия: точно один эффект для принятого ключа; длительное хранение результатов и потенциальное ожидание блокировки. Таблица без FK к счетам исключает ранние KEY SHARE locks до детерминированного FOR UPDATE. Перед добавлением multi-tenancy ключ должен получить tenant scope, проверяемый авторизацией. TTL без отдельной модели защиты старых команд недопустим.
