# ADR 004: единый журнал операций и внешний источник

Статус: принято.

Контекст: депозит тоже должен иметь двойную запись. Технический источник нельзя представить обычным кошельком с бесконечным остатком или нарушением CHECK balance >= 0.

Решение: transfers хранит kind TRANSFER/DEPOSIT. У DEPOSIT from_account_id NULL; дебет журнала адресован именованному внешнему контрагенту external:funding, кредит — пользовательскому счёту. В каждой проводке указан либо account_id, либо external_account. Каждый COMPLETED имеет ровно два совпадающих по сумме и валюте debit/credit, FAILED — ноль. PENDING запрещён на commit в синхронном сервисе. Переводы и проводки append-only; исправление возможно новым компенсирующим переводом.

Deferred constraint triggers проверяют соответствие проводок операции и balance = SUM(credit − debit) для пользовательских счетов. Триггеры не меняют баланс автоматически: его явно обновляет транзакционный адаптер. При бизнес-отказе существующих разных счетов сохраняется FAILED; при недопустимых FK/self-transfer — только результат идемпотентности.

Последствия: одна модель ответа и один протокол идемпотентности для обеих команд. Отдельного HTTP-ресурса deposits нет. Проекция проверяется суммированием истории, что подходит для демонстрации сильных гарантий, но дорого для горячих счетов с большой историей. Оптимизация требует бенчмарков и новой ADR с контрольными точками/reconciliation, а не удаления проверки без замены. Внешний источник представляет факт поступления, его подтверждение вне сервиса.
